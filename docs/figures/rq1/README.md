# RQ1 figures: captions and findings

Generated by `scripts/plot_rq1.py` from `rq1_{llama31_8b,mistral_nemo_12b,qwen15_14b}.csv`
(139,258 requests, single NVIDIA L40S). GB10 points in Fig. 1 come from the RQ4 report.
Numbers below are from `rq1_per_config.csv`, `rq1_output_length.csv` and `rq1_max_num_seqs.csv`.

Units: preemption counts are **per rate config**. The vLLM counter starts at 0 in every
rate config (one fresh server each), so L40S and GB10 counts are directly comparable.

---

## Fig. 1 — `fig_rq1_1_kv_vs_preemption` (column)

**Caption.** Peak KV-cache use vs. preemptions per rate configuration (vLLM). Filled: L40S;
hollow: GB10. Every configuration that preempts has a saturated KV pool; none below 100% does.

**Finding.** Preemption is a threshold effect of pool saturation, not a graded function of
architecture. All 30 preempting L40S configurations peak at ≥ 99.9% KV use; all 70
non-preempting ones peak at ≤ 65%. GB10 adds a larger pool and the same rule holds.

## Fig. 2 — `fig_rq1_2_saturation_timeline` (text width)

**Caption.** KV-cache use and cumulative preemptions over one run (vLLM, `mixed_real`,
concurrency 256, `max_num_seqs` 256, 16 req/s Poisson).

**Finding.** The two preempting models fail differently. Llama-3.1-8B hits a saturation spike
(98%) at ≈19 s and preempts 101 times in one burst, then stays near 100% without further
preemption. Qwen1.5-14B saturates
almost immediately and preempts continuously (379 events over ≈280 s). Mistral-NeMo peaks
at 65% and recovers.

## Fig. 3 — `fig_rq1_3_output_length` (column)

**Caption.** Output tokens per successful `mixed_real` request. Left: reasoning prompts;
right: all other task types.

**Finding — confound.** On identical prompts, the three models produce identical output
lengths for chat, code and summarization (mean 124–132 tokens), but not for reasoning:
Llama-3.1-8B averages **5,339 tokens** (median 5,861; 34% reach ≥ 8,000 tokens, near the 8,192-token context),
versus 829 for Mistral-NeMo and 826 for Qwen1.5. Llama preempts only under `mixed_real`,
the workload that contains these prompts. Its preemption is therefore driven by output
length (the prompts are not chat-templated, §2.5), not by attention architecture.

## Fig. 4 — `fig_rq1_4_itl_cost` (column)

**Caption.** Maximum inter-token latency per request (vLLM, `mixed_real`, concurrency 256,
`max_num_seqs` 256), for requests during which the server preempted (dashed) or did not (solid).
"During which" is server-wide: it marks overlap, not that the request itself was evicted.

**Finding.** Preemption is paid for in stalls. Llama: median max ITL 142 ms without
preemption vs 815 ms with, and the 90th percentile reaches **203 s**, consistent with
evicted sequences re-queued behind ≈200 waiting requests before recompute. Qwen1.5:
171 ms vs 360 ms median, 2.2 s at p90.

## Fig. 5 — `fig_rq1_5_engine_policy` (text width)

**Caption.** Running and waiting sequences over one run, and TTFT, for Qwen1.5-14B
(`mixed_real`, concurrency 256, `max_num_seqs` 256, 16 req/s). TensorRT-LLM does not
expose these counters live.

**Finding.** Under full-MHA KV pressure the admission limit is the KV pool, not
`max_num_seqs`: vLLM never runs more than 64–83 sequences and SGLang 41–60, with ≈230
waiting on both. Every engine is queue-bound. vLLM preempts the most and still drains
fastest: TTFT p50 102 s (vLLM), 142 s (SGLang), 271 s (TensorRT-LLM, with 265 of 500
requests timing out). Preemption is a symptom of pressure, not the cause of poor latency.

## Fig. 6 — `fig_rq1_6_max_num_seqs` (text width)

**Caption.** `max_num_seqs` 64 vs 256 (`mixed_real`, concurrency 256): vLLM preemptions,
TTFT p95, and completed requests/s, per model and engine. Medians over rate configs.

**Finding.** `max_num_seqs` matters only when it, not the KV pool, is the binding limit.
For Llama-3.1-8B, 64 slots fill with long reasoning generations and TTFT p95 reaches
202 s (vLLM) / 286 s (SGLang); at 256 it drops to 0.3 s, and vLLM preempts instead
(579 → 977). For Qwen1.5 the KV pool binds first, so the setting changes nothing
(TTFT p95 ≈147 s, 1,552 vs 1,678 preemptions). Mistral-NeMo is unaffected.

## Implications for the draft

1. **§3.2 must be rewritten.** Llama's preemption is explained by output length (Fig. 3),
   not by pool size or workload shape alone. Llama is not a GQA counter-example.
2. **The RQ1 claim becomes cleaner:** at matched output length, only the full-MHA model
   saturates the pool. Consider re-running Llama with its chat template (or a hard
   `max_tokens` matched to the other models) to confirm.
3. **§2.5 is incomplete.** 5,078 Mistral-NeMo requests (11%) failed with
   "no tokens received", across all three engines. This is the same zero-token
   behaviour reported for Qwen1.5 and lowers Mistral's effective load. Mistral's
   `chat_multiturn` runs also contain ≈1,395 requests vs ≈2,990 for Llama.
4. **TensorRT-LLM** reports no live KV, running/waiting or preemption values in RQ1; its
   latency hits the 300 s timeout in several cells (TTFT p95 ≈ 299 s), so its
   percentiles are censored.
