# RQ2 · Prefill handling: what prefix caching and chunked prefill buy, per engine

Generated by `scripts/plot_rq2.py` (PDF). Mistral-NeMo-12B, L40S, concurrency 256, max_num_seqs 256,
five arrival processes; prefix caching on/off × chunked prefill off/512 tokens; workloads
`chat_multiturn` (multi-turn, TTFT from send) and `chat_real_long` (≥500-token prompts, TTFT from
arrival). Prompts longer than the 8,192-token context (1% of `chat_real_long`, identical on every
engine) are rejected before sending and excluded. Numbers are in the CSVs next to each figure.

## Flow
1. **F1 payoff matrix:** what each feature does to each engine, on every metric (headline).
2. **F2 prefix caching by turn:** why prefix caching helps (it removes the prompt-growth cost).
3. **F3 chunked prefill under load:** whether chunking helps time to first token (only TensorRT-LLM).
4. **F4 chunked prefill and stalls:** what chunking is really for (smooth streaming), and where it fails (SGLang).
5. Supplementary: **S1** TTFT–TPOT trade-off arrows, **S2** strict goodput per strategy.

## F1 · `fig_rq2_1_payoff_matrix.pdf`
**Caption.** Change in TTFT p95, TPOT p95, longest token gap p95 and E2E p50 relative to both
features off, per feature and engine. Purple = better, red = worse.

**Insight.**
- Prefix caching is a uniform win on multi-turn traffic: TTFT p95 −49 to −56%, TPOT p95 −12 to
  −15%, E2E −11% on every engine. On single-turn long prompts there is nothing to reuse and it
  changes almost nothing (≤ 9%).
- Chunked prefill is engine-specific. On vLLM and TensorRT-LLM it removes stalls (longest gap
  −73 to −91%) at the cost of a slower first token on short multi-turn prompts (+60 to +67%
  TTFT p95, still ≈0.3 s). On SGLang it makes every metric worse on both workloads.
- With both features on, prefix caching recovers most of chunking's TTFT cost on multi-turn
  traffic (vLLM −37%, TensorRT-LLM −40%), so "both on" is the best setting for vLLM and
  TensorRT-LLM; for SGLang, prefix caching alone is best.

## F2 · `fig_rq2_2_prefix_by_turn.pdf`
**Caption.** TTFT p50 and TPOT p50 by conversation turn, prefix caching on (solid) vs off
(dashed), chunking off. Top axis: median prompt length.

**Insight.** Without prefix caching, TTFT grows with the conversation (≈0.1 s at turn 1 to
0.30–0.32 s at turn 6, as the prompt reaches 1.6k tokens). With it, TTFT stays flat from turn 2
(vLLM ≈0.12 s, SGLang ≈0.14 s, TensorRT-LLM ≈0.16 s). TPOT also drops by 3–10 ms per token:
skipping recomputation frees decode iterations for everyone, not just the cached request.

## F3 · `fig_rq2_3_chunked_under_load.pdf`
**Caption.** TTFT p95 vs arrival rate on long prompts, chunked prefill (solid) vs not (dashed),
prefix caching on.

**Insight.** All three engines saturate on long prompts beyond 2 req/s (TTFT p95 ≈40–110 s).
Chunking costs a little at light load (2 req/s: ≈0.7 → 1.1 s) because a long prompt now needs
several iterations. Under load only TensorRT-LLM benefits (4 req/s: 44 → 31 s, −28%); vLLM is
unchanged and SGLang gets slower.

## F4 · `fig_rq2_4_chunked_stalls.pdf`
**Caption.** ECDF of the longest token gap per request, chunked prefill (solid) vs not (dashed),
prefix caching on.

**Insight.** Chunked prefill exists to stop long prefills from freezing running streams, and on
vLLM and TensorRT-LLM it does: the p95 longest gap on long prompts falls from ≈1.1 s to 0.31 s
(vLLM) and from 1.02 s to 0.12 s (TensorRT-LLM). On SGLang the stalls are already the longest
(p95 4.1 s) and get worse with chunking (6.1 s). TODO: check whether SGLang's "no chunking"
setting still used its default chunk size, which would explain why the 512-token setting adds
overhead without removing stalls.

## S1 · `fig_rq2_s1_chunk_tradeoff.pdf` (supplementary)
**Caption.** TTFT p95 vs TPOT p95, arrow from chunking off to on, prefix caching on.

**Insight.** On long prompts TensorRT-LLM and vLLM move down (faster decode), TensorRT-LLM also
left (faster first token); SGLang moves up and right. On multi-turn traffic chunking moves every
engine right (slower first token) with little change in TPOT.

## S2 · `fig_rq2_s2_goodput.pdf` (supplementary)
**Caption.** Strict goodput (TTFT ≤ 2 s, TPOT ≤ 200 ms) per strategy and engine.

**Insight.** Goodput does not separate the strategies: 100% everywhere on multi-turn traffic at
this load, and 40–46% on long prompts for every engine, where queueing on prefill, not the
feature choice, decides TTFT. Chunking lowers it by 2–5 points because of its light-load TTFT
cost. The features matter for tail latency and streaming smoothness (F1, F4), not for this SLO.

---

## Recommendation (for the decision table)
| Engine | Multi-turn chat | Long prompts |
|---|---|---|
| vLLM | prefix caching + chunked prefill | chunked prefill (smoother streaming) |
| SGLang | prefix caching, no extra chunking | no extra chunking |
| TensorRT-LLM | prefix caching + chunked prefill | chunked prefill (better on every metric) |

## Caveats
- One model (Mistral-NeMo-12B) and one load level per arrival process; one run per configuration.
- Engine chunk-size semantics differ; "no chunking" may not disable chunking on every engine.
- TensorRT-LLM's chunked-prefill strategy sets `enable_chunked_prefill` explicitly (without it the
  chunk size acts as a hard prompt-length limit).
