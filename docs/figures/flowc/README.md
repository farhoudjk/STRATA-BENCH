# RQ1 · Flow C — "Which engine should I deploy?"

Generated by `scripts/plot_flowc.py` from the RQ1 per-request CSVs (L40S, concurrency 256,
max_num_seqs 256 unless stated). Every number below is in the CSV next to its figure.

## C1 · Metrics and SLOs (table)

| Metric | Definition | What the user feels |
|---|---|---|
| TTFT | first token − arrival (`mixed_real`, open loop: send-based TTFT + client queueing); first token − send (`chat_multiturn`, closed loop: later turns are held by design) | responsiveness |
| TBT | gap between streamed chunks, per request (p95 and max) | smoothness / stalls |
| TPOT | (E2E − TTFT) / (output tokens − 1) | generation speed |
| E2E | arrival → last token | task completion |
| Throughput | output tokens/s over the run | capacity, cost |
| Outcome | finished · zero-token reply · timeout | reliability |
| Goodput | % of **all** requests that finish with TTFT ≤ *a* and TPOT ≤ *b* | the combined verdict |

SLO tiers: **strict** TTFT ≤ 2 s, TPOT ≤ 200 ms · **relaxed** TTFT ≤ 4 s, TPOT ≤ 500 ms ·
supplementary **tight-TPOT** TTFT ≤ 4 s, TPOT ≤ 50 ms.

Censoring: requests with no first token within 300 s count as TTFT = 300 s and E2E ≥ 300 s;
requests that started but did not finish within 600 s count as E2E = 600 s. Zero-token replies
(a model/prompt failure) are excluded from latency and count as goodput misses.

## C2 · `fig_c2_load_response` — latency and throughput as load rises
**Caption.** TTFT p95 (from arrival), TPOT p95 and output throughput vs. Poisson arrival rate,
`mixed_real`. Dashed lines: SLO targets.

**Insight.** On Mistral, vLLM holds TTFT p95 under 1 s up to 16 req/s and SGLang up to 8 req/s;
on Llama both stay under 0.4 s from 4 req/s up (at 2 req/s late arrivals meet a KV pool already
full of long generations, ≈150–185 s). TensorRT-LLM never gets below 37 s on mixed traffic. TPOT stays well below 200 ms for every engine except
vLLM on Llama at 2 req/s (277 ms, preemption stalls). Throughput is set by admission, not
decode speed: on Qwen vLLM sustains ≈410 tok/s, SGLang ≈235, TensorRT-LLM ≈100.

## C3 · `fig_c3_streaming_quality` — once a response starts
**Caption.** ECDFs of per-request TPOT (top) and longest token gap (bottom), finished requests
with > 20 tokens, `mixed_real`.

**Insight.** TensorRT-LLM streams fastest and steadiest: TPOT p50 41–43 ms, p95 48–49 ms, no
gap above 0.6 s. vLLM's median is similar (48 ms) but its tail is long — TPOT p95 ≈100 ms and,
on Llama, a p95 longest gap of **125 s** (7% of requests stall > 1 s; 19% on Qwen): preempted
sequences wait to be recomputed. SGLang sits between, with no stalls above 1 s except Llama (4%).

## C4 · `fig_c4_e2e` — end-to-end latency
**Caption.** E2E from arrival, p50 (filled) and p99 (hollow), timeouts counted at 300/600 s.

**Insight.** The ranking flips with the workload. Uniform `chat_multiturn`: TensorRT-LLM is
fastest (Llama p50 12.4 s vs 13.3 vLLM, 14.2 SGLang). Mixed `mixed_real`: TensorRT-LLM is
slowest by far (Llama p50 **278 s** vs 5.4 s vLLM); its first-token wait dominates.

## C5 + C6 · `fig_c5_c6_outcomes_goodput` — reliability and SLO goodput
**Caption.** Left: how requests end. Right: % of all requests meeting each SLO tier
(bold = best engine per row).

**Insight.**
- Zero-token replies are identical across engines (Mistral ≈17% on `chat_multiturn`, ≈7% on
  `mixed_real`): a model/prompt failure. Timeouts are engine-specific: TensorRT-LLM loses
  41% of Qwen and 18% of Llama `mixed_real` requests; vLLM and SGLang lose 0–8%.
- Goodput: vLLM leads every mixed workload (strict 88 / 93 / 25% vs SGLang 87 / 80 / 4% vs
  TensorRT-LLM 28 / 40 / 2%). On uniform chat the engines tie.
- **TTFT decides goodput, not TPOT**: requests that miss only the TPOT target are ≤ 2% in every
  cell, so relaxing to 4 s / 500 ms changes results by ≤ 5 points.

## C7 · `fig_c7_max_num_seqs` — what raising max_num_seqs buys
**Caption.** max_num_seqs 64 → 256, `mixed_real`: strict goodput, TTFT p95, TPOT p95.

**Insight.** Where scheduler slots bind (Llama, Mistral), 256 roughly doubles vLLM/SGLang
goodput (Llama 46 → 88%) and cuts vLLM's TTFT p95 from ≈280 s to 0.35 s — paid for with a
higher TPOT tail (73 → 97 ms) because more sequences share each step. Where KV memory binds
(Qwen) or admission is reservation-based (TensorRT-LLM), the setting changes nothing.

## S1 · `fig_s1_tight_tpot_goodput` (supplementary) — a tight TPOT target changes the winner
**Caption.** Goodput under strict, tight-TPOT (4 s / 50 ms), and TPOT-only (≤ 50 ms) targets.

**Insight.** With a 50 ms TPOT target TensorRT-LLM wins every uniform-traffic cell (Llama chat
96% vs 74% vLLM, 60% SGLang) and has by far the most requests within 50 ms on mixed traffic
(81–89% on Llama and Mistral vs ≤ 52% for the others) — but its first-token wait still caps mixed-traffic goodput. The verdict depends on
which latency the application is bound by.

## C8 · Decision matrix (table)

| Situation | Pick | Evidence |
|---|---|---|
| Uniform request shapes, steady load | **TensorRT-LLM** | lowest E2E on chat (C4); TPOT p95 ≈49 ms (C3); wins tight-TPOT goodput (S1) |
| Mixed request lengths, TTFT-bound SLO | **vLLM** | highest goodput on every mixed cell (C6); highest throughput on Qwen (C2) |
| Streaming smoothness matters (voice, agents) | **SGLang** or TensorRT-LLM | no multi-second stalls (C3); vLLM stalls up to 125 s at p95 on Llama |
| Model barely fits in KV memory | **vLLM**, and more memory | only engine above 5% goodput on Qwen `mixed_real` (C6) |
| Slot-bound deployment | raise `max_num_seqs` | goodput ×2 for vLLM/SGLang (C7); no effect when KV binds |
| Choosing by published tokens/s | **don't** | fastest decoder has the lowest mixed-traffic goodput (C3 vs C6) |

## Caveats to carry into the paper
- One run per configuration; no confidence intervals.
- TensorRT-LLM's admission behaviour should be confirmed against its launch configuration
  (capacity-scheduler policy) before it is attributed to the engine.
- Llama-3.1-8B produces ≈6× longer reasoning outputs than the other models (prompts are not
  chat-templated), which raises its KV pressure on `mixed_real`.
